**v1.13.1까지 실패한 진짜 이유**: 로그인 창과 **별도의 크롬**을 띄우고 프로필(쿠키)만
복사했다. 그런데 크롬 127+는 쿠키를 **앱에 묶어 암호화(App-Bound Encryption)** 해서
**복사한 쿠키를 다른 크롬 프로세스가 풀지 못한다.** → 로그인해 둬도 수집 쪽은
로그아웃 상태로 페이지를 읽었다. WAL·엔진·프로필 위치를 아무리 고쳐도 이 벽은 못 넘는다.

**예정 수정 — [🌐 내 크롬 열기(로그인)] 방식**
1. 쇼핑 카드에 **[🌐 내 크롬 열기]** 버튼 — 컷대장 전용 크롬 프로필
   (`cutdaejang_chrome`)로 크롬을 **눈에 보이게** 띄운다. 회원님은 거기서
   쿠팡·네이버에 **한 번만 로그인**한다(세션은 그 프로필에 남는다).
2. 수집할 때는 **같은 프로필**로 헤드리스를 띄운다 → 쿠키·로그인이 그대로 따라온다.
   (지금 `_browser_args`의 프로필만 바꾸면 되는 구조)
3. 로그인 창이 켜져 있으면 같은 프로필로 두 번 못 띄우므로, 프로필을 임시 복제해
   쓰거나 "로그인 창을 닫아 주세요" 안내를 띄운다.
4. 화면에 **로그인 상태 표시** — "✅ 쿠팡 로그인됨 / ⚠ 로그인 안 됨"
- 부수 수정: 새 링크로 수집을 시작하면 **「수집 결과」 칸의 옛 내용을 비운다**.

  보인다 — 실제로는 임시 저장된 옛 글이 그대로 보이는 것.
- 이전 분석(_usable 관대함 / download_images 12KB 하한)은 **2차 원인**으로 유효하나,
  1차 원인은 위 로그인 문제다.

**남은 선택지 (회원님 판단)**: 4K 자체를 더 빠르게 하려면 화질을 낮추는 수밖에 없는데,
회원님은 유튜브 노출 때문에 4K를 쓰신다고 하셨으므로 **손대지 않았다.**

```
"status": "RESOURCE_EXHAUSTED"
```
**「선불(prepay) 크레딧이 다 떨어졌다」** — 모델 문제가 아니고, 분당 한도도 아니다.
- 회원님이 보시는 **4만원 한도 / 600원 사용**은 «사용량·상한» 화면이고,
  **선불 크레딧 잔액은 별도**다. 잔액이 0이면 상한이 남아 있어도 호출이 막힌다.
- 회원님 시도: "다른 프로젝트의 키를 썼는데도 똑같다" → **당연하다.**
  선불 크레딧은 **프로젝트가 아니라 결제 계정**에 붙어 있어서 프로젝트를 바꿔도 같다.

  ①**선불 크레딧 충전** 또는 ②**후불(pay-as-you-go)로 전환**.

**우리 판정기는 이 경우를 이미 맞게 분류하고 있었다** (실측):
```
is_daily_quota(선불 소진)  = True   → 기다려도 안 풀림 (재시도 안 함) ✔
is_daily_quota(분당 한도)  = False  → 재시도 대상 ✔
```
→ 남은 문제는 **화면 문구**와 **재시도가 대본 경로에 없다**는 것 두 가지다.

**결론: 이번 건 자체는 회원님 결제 상태가 원인. 다만 우리 메시지가 오해를 키웠다.**

**원인 (코드 확정)**
1. `webui.py` 3193행 — POST 전역 가드가 **문자열만 대충 보고** 판정한다.
   ```python
   if "429" in s and ("credit" in s.lower() or "RESOURCE_EXHAUSTED" in s
                      or "quota" in s.lower()):
       msg = "Gemini 한도·크레딧이 소진돼 …무료 한도는 내일 오후 4~5시쯤 풀리고…"
   ```
   그런데 제미나이는 **성격이 완전히 다른 두 가지**에 똑같이 429를 준다.
   | 종류 | 뜻 | 대응 |
   |---|---|---|
   | 하루 한도·크레딧 소진 | 기다려도 오늘은 안 풀림 | 내일 / 충전 |
   | **분당 요청·토큰 한도(RPM/TPM)** | **몇십 초면 풀림** | **잠깐 뒤 재시도** |

   그리고 **분당 한도 응답에도** `RESOURCE_EXHAUSTED`와 `quota`가 그대로 들어 있다
   (`quotaId: GenerateRequestsPerMinutePerProjectPerModel`).
   → 잠깐 기다리면 될 일을 **"크레딧 소진, 내일 오후에 풀려요"** 로 잘못 알린다.
   유료 키를 쓰는 회원님께는 완전히 헛다리다.

2. 🔴 **이미 있는 올바른 판정기를 대본 쪽에서 안 쓰고 있었다.**
   `tts_engine.is_daily_quota()`는 `quotaId`에 `perday`가 있는지, 본문에
   `prepayment credit / credits are depleted`가 있는지를 봐서 **진짜 소진과 분당
   한도를 구분**한다(v0.50.2/v0.51에 목소리 쪽 문제로 만들어 둔 것).
   `parse_retry_delay_s()`로 **서버가 알려준 대기 시간**(`retryDelay: "39s"`)도 읽는다.
   그런데 `script_generator.py`는 이걸 **한 번도 안 쓴다** — 실측:
   ```
   grep -c "except TTSHTTPError|is_daily_quota|parse_retry_delay_s"
     script_generator.py → 0
   ```
   제미나이 호출 **10곳 전부** `_http_post_json`을 그냥 부르고 끝이라,
   **재시도도 없고 레이트리미터도 없다.** 목소리(TTS) 쪽만 v0.50.2에서 손봤고
   대본·업로드 키트 쪽은 그대로 남아 있었다.

3. 업로드 키트는 **영상 캡처 4장 + 대본 전문**을 한 번에 보내는 큰 멀티모달 요청이라
   (`extract_frames_b64(mp4, n=4)`) **분당 토큰 한도(TPM)** 에 걸리기 쉽다.

**수정안 (회원님 확인 후)**
- ㉮ 대본·키트 호출에도 `is_daily_quota` 적용 — **분당 한도면 서버가 준 `retryDelay`만큼
  기다렸다 자동 재시도**(2~3회). 대부분 회원님은 실패 자체를 못 느끼게 된다
- ㉯ 진짜 소진일 때만 지금 문구를 쓰고, 분당 한도면
  **"잠깐 몰려서 밀렸어요 — 자동으로 다시 시도 중"** 으로 분리

- ㉱ 대본 호출에도 레이트리미터 적용(목소리 쪽처럼)

**🔴 지금 문구의 가장 나쁜 점**: 선불 크레딧이 떨어진 건데
「**무료 한도는 내일 오후 4~5시쯤 풀리고**」라고 앞세운다.

### 9. 구간마다 [화면] 메모 · 나레이션 · [자막] 을 따로 넣기 — ✅ **v1.13.0 완료** (3칸 + 촬영 대본 자동 분리 + 무낭독 카드)

### 13. 구간 영상이 4K→1080p→4K를 왕복해 3번 인코딩됨 — ✅ **v1.11.1 수정 완료**
- 증상(2026-07-28): 3분짜리를 구간으로 나눠 클립 넣고 제작 → **45분째 98%**
  화면 문구: `합본 위에 내레이션과 자막을 같은 시간표로 입히는 중…`
- **회원님 증언: 예전에 같은 3분·초고화질(4K)은 이렇게 오래 안 걸렸다** → 회귀 확정
- ※ 조사 초기에 "회원님이 v1.11.0보다 새 빌드를 쓰는 것 같다"고 적었던 것은 **오판**.
  컨테이너 초기화로 옛 코드(v0.84)를 검색해 생긴 착오였고, 보내주신 v1.11.0 zip과
  저장소 코드는 **프로그램 파일 142개 전부 동일**함을 해시로 확인했다.

**원인(코드 확인 완료) — 가로(wide) + 초고화질(ultra) 기준**
| 단계 | 코드 | 실제 동작 |
|---|---|---|
| ① 구간별 화면 렌더 | `webui.py` 2240행 `layout="wide", quality="ultra"` | `_FIXED_CANVAS["wide"]=(1920,1080)` × `ultra mult=2.0` → **4K(3840×2160)로 렌더** (구간 수만큼) |
| ② 이어붙이기 | `webui.py` 2271행 `concat_videos(..., size=(1920,1080))` | **4K 구간들을 1080p로 다운스케일**해 합침 ← 인코딩 2회차 + 화질 손실 |
| ③ 자막·내레이션 입히기 | `webui.py` 2294행 `layout="keep", quality="ultra"` | `keep`은 원본 기준 배수 → 1080p × 2.0 = **다시 4K로 업스케일**하며 자막 굽기 + `cas` 선명화 ← 인코딩 3회차 |

- **결과: 4K → 1080p → 4K 왕복. 전체 인코딩 3회** (예전 2회: 구간 렌더 + 합치기)
- 손해가 둘
  1. **시간** — 4K 전체 인코딩이 한 번 더 늘었고, 마지막 패스는 4K + libass 자막 굽기
     (CPU 작업) + 선명화가 겹쳐 가장 무겁다
  2. **화질** — 1080p로 줄였다 늘린 것이라 **진짜 4K가 아니라 1080p 업스케일**.
     4K 업로드로 노출을 얻으려는 목적이 반감된다
- 부수 확인: 진행률 **98%는 고정값**(`frac=0.975~0.989` 구간) — 실제 진행률이 아님 → 14번
- 회원님 자막 등장 효과가 **"타이핑"(`anim: "type"`)** 이라 4K 자막 굽기 부담이 더 큼

**예정 수정 (권장안)**
- **구간은 1080p로 가볍게 렌더 → 마지막 한 번만 4K로 올리며 자막 굽기**
  - 인코딩 실질 2회, 업스케일 1회 → **시간 크게 감소 + 화질은 지금보다 향상**
  - 구현: ① 구간 렌더는 `quality`를 `standard/high`로 고정(또는 mult=1.0),
    ② `concat_videos`의 `size`를 최종 캔버스와 일치시키고,
    ③ 최종 패스에서만 ultra 배수를 적용
- 대안: `concat_videos(size=...)`를 4K로 맞춰 다운스케일을 없애고 최종 패스는 mult=1.0
- ⚠ **화질을 낮추는 건 해법이 아님** — 회원님은 유튜브 노출 때문에 4K로 올린다
